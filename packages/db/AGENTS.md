# Database module conventions

`@kobato/db` owns the content database's SQLite/Drizzle implementation AND the DuckDB analytics sidecar's persistence layer: connection primitives, schema, row types, query operations, migrations, SQLite error classification, and the DuckDB DDL/appender/query modules. It depends on the shared leaf packages it needs (`@kobato/settings`, `@kobato/lexical`, `@kobato/utils`), never on `@kobato/contracts` (the wire), `@kobato/server`, `@kobato/web-admin`, or `@kobato/ui`.

- Callers import source modules directly as `@kobato/db/<path>.ts`; there is no barrel.
- Engine planes: `src/` root, `schema/`, and `operations/` are the SQLite/Drizzle plane; `duckdb/` is the analytics plane. A module belongs to exactly one plane, with `database.ts` (the shared `:memory:` path sentinels) the only crossing. `types.ts` and `target.ts` are SQLite-plane row types — not a shared vocabulary.
- `drizzle/` contains the package-owned SQL migrations and the latest drizzle-kit snapshot. It ships as package source through the `@kobato/db/drizzle/*` export; `src/migrate.ts` resolves this directory through the `@kobato/db/package.json` export outside SEA. See `drizzle/AGENTS.md`.
- `drizzle.config.ts` lives at the package root, anchored on this package's cwd (`schema: ./src/schema/**/*.ts`, `out: ./drizzle`); the package scripts `db:gen` / `db:migrate` run drizzle-kit, and the workspace-root `pnpm run db:gen` / `db:migrate` forward here via `pnpm -C`.
- `database.ts` owns `node:sqlite` + Drizzle's synchronous driver and the `:memory:` sentinel (`isInMemoryPath`/`resolveStoragePath`, shared by both engines). Configuration-specific path selection stays in the server composition layer.
- `duckdb/` owns the analytics sidecar's persistence: `database.ts` (the engine handle — open/close, one instance + reader/writer connections, the 2.0 storage-format upgrade with an injected `DuckDBLogger`; zero business knowledge), `schema.ts` (the complete `ANALYTICS_DDL`/`ANALYTICS_TABLES` list), `access-events.ts` (the `access_events` DDL, the `blobsMap`/`doublesMap` slot contracts plus the derived semantic-name→slot `blobColumns` reverse map, the `EnrichedAccessEvent` row type, `index1Of`, and the chunk-based `appendAccessEvents`), `device-env.ts` (both `device_env_*` DDLs, row types, appenders, and `existingDeviceEnvEventIds` dedup probes), `maintenance.ts` (the 180-day retention DELETE + CHECKPOINT), `blob-migration.ts` (the legacy `access_log` one-shot conversion; the SQLite flag rides `@kobato/db/operations/setting.ts`), and `query.ts` (Kysely as a compile-only SQL builder — DummyDriver, identifier whitelist, bound parameters only — plus the `executeAnalyticsQuery` runAndReadAll core and the `setAnalyticsQueryExecutor` seam). DuckDB open/maintenance/blob-migration diagnostics log through an INJECTED `DuckDBLogger` (the composition layer passes its logger, mirroring `migrate.ts`'s `MigrationLogger`) — this package never reaches for a logger itself and never imports server trace. The dashboard read queries live in `duckdb/queries/` (views, heatmap, counters, metric, realtime tail, export rows, aggregates, query-filter, metric-dimensions); `duckdb/queries/types.ts` owns the analytics persistence query vocabulary — `ResolvedAnalyticsQuery`, the counters/views/heatmap/metric/realtime output shapes, and the pure time primitives (`computeDateRange`, `pickTimeUnit`, the preset/time-unit/metric-type lists). Their wire twins live in `@kobato/contracts/analytics`; the server maps wire input onto the resolved query and the outputs back onto the HTTP DTOs. `parseAnalyticsSearch` URL parsing, SSE connection caps, CSV serialization, overview fan-out, and every lifecycle concern (engine boot, mutation lock, batchers, scheduling, telemetry wiring) stay in `@kobato/server`. Test setups reset the executor to `null` after each test.
- `schema/` contains only persistence schema, including the persistence-canonical enum lists (`webmention.ts`, `notification.ts`, `job-run.ts`, `user.ts` login methods, `storage-migration.ts`) that generate the drizzle `text({ enum })` columns and the SQL CHECK literals. Domain validation and wire DTOs stay in `@kobato/contracts` or the owning server domain — every duplicated list is pinned value-identical by `packages/server/tests/unit/server/infra/db/wire-parity.test.ts` (the server is the one place both vocabularies are importable).
- `operations/` contains reusable Drizzle queries and engine operations, including `maintenance.ts` (`vacuumDatabaseInto` and `analyzeDatabase`). Domain orchestration and transport errors stay in `@kobato/server`.
- `migrate.ts` owns migration execution, package/SEA folder selection inputs, lifecycle logging, and failure propagation. The server composition root only injects its `MigrationLogger` and optional SEA folder; restore receives the composed function through `RestoreCompletionDeps`.
- Process lifecycle, batchers, schedulers, path resolution, and observability remain in `@kobato/server`; no server import is needed here.
- Imports within this package use the package root (`@kobato/db/...`), not relative traversal.
