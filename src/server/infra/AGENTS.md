# Infra conventions

`src/server/infra/` holds technical primitives (layer rules live in `../AGENTS.md`). This file pins the contracts that are easy to break: the config-file surface and the SEA runtime asset rules.

## Config file

Infrastructure configuration lives in `kobato.config.json` — auto-created with defaults when missing. `src/server/infra/config.ts`'s `CONFIG_TABLE` maps nested config paths to Zod schemas; consumers read the validated `serverConfig` export. Env var names are derived by convention (`path.join('__')` → `storage__database`).

- Location order: `--config <path>` → `KOBATO_CONFIG_FILE` (dev tooling; resolved against cwd, treated as explicit) → SEA `<execDir>/kobato.config.json` → `./kobato.config.json` → `~/.config/kobato.config.json`. First existing wins unless an explicit `--config`/env path was supplied.
- Precedence: schema defaults < config file < env vars. Env values differing from the file are written back (coerced to native JSON types only when the entry's schema accepts the coercion — a numeric-looking secret stays a string). `security.trustedProxies` rejects `0.0.0.0/0` (it would trust proxy headers from any peer, disabling every per-IP rate limit).
- `VITEST=true` without `--config` → env-only, zero filesystem access.
- Tooling that spawns the binary MUST pass `--config <tempDir>/…` to avoid persisting throwaway config next to the binary.
- Adding a config value: add a `CONFIG_TABLE` row → update `kobato.config.example.json` → cover it in `tests/unit/server/infra/config.test.ts`.
- `trace.*` (ADR-0012) is a boot-time snapshot that never gates boot: `infra/trace/config.ts` validates endpoint security, the organization path grammar, credential completeness, and sampling ranges, then safely disables the affected pipeline and logs field names only. Production always ignores `trace.enabled`. In a DEV build `server.ts` dynamically imports `infra/trace/runtime.ts` (the only OTel SDK importer): a fixed three-key resource for both signals, ParentBased ratio sampler, W3C `tracecontext` extraction, bounded BatchSpanProcessor (1024 queue / 256 batch / 1s delay / 3s timeout), a `PeriodicExportingMetricReader` (10s collection / 3s export, OTLP exporter with `temporalityPreference: DELTA` so `_sum`/`_count` streams are per-interval increments) posting to OpenObserve `/v1/metrics`, direct OTLP/HTTP export, the `perf_hooks` event-loop gauge, and the trace-only SQLite diagnostics subscriber (`sqlite.ts`, independent of the debug-log subscriber and opt-in under Vitest). Starts/stops are idempotent; every cleanup action (delegate uninstall, shutdown-hook removal, observer disable, SQLite unsubscribe) is independently exception-isolated, and `forceFlush`/`shutdown` race tracer and meter through one bounded timeout; HMR disables the observer and both providers before reinitialization. A failure anywhere in the post-provider startup tail runs one idempotent rollback (no-op facade, observer, SQLite subscriber, shutdown hook, both providers) and never throws into the application. Disabled/invalid config never constructs a provider. Metric names/attribute keys are a closed catalog in `metrics.ts`; non-finite values and invalid declared dimensions are dropped. The optional local OpenObserve instance, four versioned dashboards, 1-day per-stream retention, RUM token/CORS setup, and the second-boundary ingest pipeline live in `scripts/trace/` (see `scripts/trace/README.md`). That pipeline is the authoritative, fail-closed RUM field boundary: it copies an explicit allowlist into a fresh event and deletes every unnamed field. `pipeline-verify.ts` probes `GET /api/<org>/pipelines` and `/functions` with the server-only OTLP credential at DEV startup (1.5s timeout), validates the shared `trace-pipeline` name/version/hash description, `_rumdata` source, `enabled === true`, exactly three nodes and two input→function→output edges (bypass/extra rejected), `after_flatten=true`, and hashes the actual stored function body (stripping O2's ` \n .` sentinel); only success activates `frontend-gate.ts`, which the root loader and CSP consume via `activeFrontendRum()`. A token-scoped 15s interval rechecks both ways; `/api/dev/rum/status` (DEV-only, `no-store`, boolean only, untraced) lets an open browser follow the gate. The interval is cleared on stop/HMR and cannot clear a newer runtime's gate. The runtime-scoped token prevents an HMR-disposed runtime from clearing its replacement's gate; failure/offline leaves server traces/metrics running and withholds browser RUM until a later 15s recheck succeeds; the same interval can disable and re-enable frontend RUM without a restart. The slim SDK's `beforeSend` only copies its declared modifiable paths, so browser-side deletes of `device`/`display`/headers/raw performance objects are not honoured; run `trace:init` before enabling frontend RUM.

## SEA runtime rules

Build-side mechanics (VFS constraints, bundles, natives, commands) live in `scripts/sea/AGENTS.md`.

- Native packages (sharp, @napi-rs/canvas, @duckdb/node-api) are statically imported like any other dependency — the bundler inlines them and the redirect plugin rewrites their platform loads. The inverted hazard is the OLD pattern: a `requireExternal('sharp' | ...)` call site hides the package from the bundler and crashes under SEA. Enforcement: the boundaries contract test bans native `requireExternal(...)` sites, and the native-specifiers test enumerates every platform `require` in the installed packages so a new specifier fails at upgrade time. `requireExternal` remains only as `nativeRequire`'s resolver.
- Runtime file reads that must work under SEA go through `seaAssetPath` (raw assets, main thread only) or `getEmbeddedAsset` (packed `natives/*` + `natives-meta/*` — the worker-safe channel). Never `seaAssetPath` a `natives/*` key (it throws — zstd bytes). New resource types go into `scripts/sea/assets.ts` AND are read via the sea helpers with a non-SEA fallback.
- Embedded asset keys are owned by `src/shared/sea/assets.ts` — new keys go there; never hardcode one in `scripts/` or `src/server/` (`tests/unit/shared/contracts/sea-assets.test.ts`).
- `KOBATO_NATIVES_DIR` / `KOBATO_CACHE_DIR` are runtime env vars read outside `config.ts`: the SEA runtime modules read them before the validated `serverConfig` snapshot exists (allowlisted in the boundaries test).
