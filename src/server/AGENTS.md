# Server conventions

`src/server/` is SSR-only: may import `shared/` and other `server/`, never `client/` or `ui/`. Four layers, strict one-way import graph:

```
server/
├── infra/    # Technical primitives — zero business knowledge.
├── domains/  # Self-contained business modules (one folder per domain).
├── http/     # HTTP perimeter (oRPC + Hono).
└── render/   # SSR output products (HTML, RSS/Atom, OG, calendar, SEO).
```

## infra/

Pure primitives; imports nothing from `domains/`, `http/`, or `render/`. Module-level contracts (config file, SEA runtime assets/env) live in `infra/AGENTS.md`.

- `db/` — `database.ts` (node:sqlite `DatabaseSync` open/close + pragma block), `migrate.ts`, drizzle schema, `operations/<entity>.ts` raw helpers; `insert-batcher` + `batcher-registry` for process-level write batchers; `maintenance.ts` daily vacuum/optimize job; `query-diagnostics.ts` 'sqlite.db.query' channel → debug-level statement timings (bound values redacted; vitest no-op).
- `job-registry.ts` — process-level background jobs self-register `(name, nextDelayMs, run)` at import time; the hydration phase arms them all with one `startAllRegisteredJobs()`. The registry owns the shared lazy db-handle getter (`setJobHandleGetter` + `jobDb()`), so adding a timer means editing only its own module — no wire preamble, no `server.ts` edit. Timer mechanics stay in `scheduler-utils::scheduleJob`; enqueue-path nudges use `nudgeRegisteredJob(name)` (no-op until started). A registration may carry a catalog `task: { key, recordHistory? }`: `scheduleJob` then exposes live per-task state (`getSchedulerTaskState` — suspended / nextRunAt / running) and, with `recordHistory`, persists each fire to `job_run` (the instrumentation backing `/admin/tasks`). `scheduleJob` owns the single `job.run` trace perimeter (registered name + catalog task key only; no entity/payload content).
- `analytics/` — the DuckDB sidecar wrapper (`duckdb.ts`: open/close/path — zero business knowledge); the table DDLs + appenders live in `domains/analytics/services/access-log` and `device-env`.
- `cache/` — `file-store` owns the on-disk plane: `<storage.data>/cache/<bucket>/<h[0:2]>/<h[2:]>` (`h = sha256(fullKey)`), the `KBC1` envelope (`expiresAtMs`, 0 = never), `_generation` counters, and the lifecycle helpers.
- `cache/memory-store` is the process-local L1 in front: a per-bucket LRU bounded on BOTH entry count and estimated bytes (a value above 64KiB never enters L1; `og`/`calendar` carry a zero budget — L1-exempt by policy, independent of value size), holding DECODED values under the disk envelope's own deadline, so a hit skips both the file read and the `JSON.parse`; expired entries evict lazily on read; L1 hits still count as `cache.lookup` hits. A memory hit hands every caller the SAME object — cache results are read-only by contract.
- `cache/registry` is the behavior plane: its verbs take NO `Database`, `through` writes are fire-and-forget (errors swallowed), and the read verbs own the `cache.lookup` span/count with only bucket/result/coalesced labels — keys and params are never recorded.
- L1 invalidation is synchronous and runs BEFORE the filesystem leg: `clear` drops a bucket, `clearLocalizedOutputs` drops the four render buckets, admin `clearBucket` drops both planes, `wipeCacheForRestore` drops everything. Process-local is sound because the SEA deployment is a single process; no cross-process coherence exists. Content invalidation (`feed`/`sitemap`) clears by synchronous unlink; admin clear of the counter bucket strictly bumps and persists `_generation` before dropping entry shards, so late writers stay unreachable. Admin stats walk each bucket once: `keyCount` counts live valid `KBC1` entries and `byteSize` sums every shard entry file (expired/malformed included). `kv-maintenance` sweeps expired entries, `_tmp` orphans and trash dirs older than an hour.
- Settings-derived render entries key on the SECTION-SCOPED representation generation (`shared/config/representation-scopes` — a content-addressed hash per `feed`/`calendar`/`og`/`manifest`/`sitemap`/`detail`/`listing` over exactly the sections that surface renders, memoized per bundle identity). The boot-unique `AppLocalization.revision` stays the request-identity / locale-sync token and never keys a cache. Unrelated saves (security/backup/mail/limits) move nothing; a relevant save orphans only its scope, and `clearLocalizedOutputs` only RECLAIMS that orphaned storage (a strict, synchronous rename-to-trash of `feed`/`calendar`/`og`/`sitemap`, reaped asynchronously). Correctness never depends on the delete or on waiting for in-flight renders — a render started before the save writes its own old-generation key.
- `http/` — `etag`, `headers`, `status`, `errors` with `DomainError` / `ActionFailure`. `email/`, `search/` (LIKE-only dispatcher), `image/` (worker_threads pool; `WorkerPool.process` records queue-vs-execution telemetry, and the inline DEV transform records the same execution boundary), `crypto/`, `config.ts` (+ `config-arg.ts` — side-effect-free `--config` argv parsing shared with `sea-cli.ts`), `i18n.ts` (the server translator: react-intl `createIntl` over the merged UI + server catalogs, cached per immutable locale, degrading to English when the catalogs fail validation), `logger.ts`, `rate-limit.ts`, `slug/`.
- `trace/` — OpenObserve tracing, metrics, and log export, configured ONLY in the `observability` settings section and driven by `domains/observability/runtime-manager.ts`. `config.ts` resolves the settings projection into a validated server projection (including `observability.logs.enabled` → a `logs` OTLP endpoint reusing the trace credential) and browser-safe RUM bootstrap (the browser gate is verified per runtime in every build; bad config safely disables). `facade.ts` is the SDK-free span/metric surface (`withSpan`/`withSpanAsync`, the manual `startSpan`/`runInSpan` lifecycle with explicit `startTime`/`end(endTime)`, and `counter`/`histogram`) that `runtime.ts` installs a delegate into; `sanitize.ts` owns the closed span-attribute/value allowlists and error projector; `metrics.ts` owns the closed metric catalog plus the boundary recording helpers; `resource.ts` owns the fixed three-key resource shared by every server signal; `log-record.ts` is the SDK-free log-line projection (closed body/attribute set, marker/scope drops); `logs-runtime.ts` builds the log pipeline (OTLP/HTTP exporter, bounded batch processor, closed log-record limits) whose sink `runtime.ts` installs into `logger/sink.ts`'s Pino-writable slot.
- `runtime.ts` and `logs-runtime.ts` are the ONLY server modules allowed to import `@opentelemetry/*`; the runtime is reached through one dynamic import in `domains/observability/runtime-manager.ts`, the log pipeline is constructed only by it, and a disabled/unverified configuration never constructs a provider/exporter/context manager/reader (a production build still carries the SDK chunk). Source guard: `tests/unit/arch/trace-sdk-boundary.test.ts`. Span seams: `middleware.ts` (Hono request), `react-router.ts` (root document/`.data`), `sqlite.ts` (trace-only `sqlite.db.query` subscriber; Vitest opts in explicitly), `route-registry.ts` (matched RR pattern carried to the Hono span through the shared Request object). Instrumentation boundaries: `safe-fetch`, the cache registry, analytics `runAnalyticsQuery`, the image pool, and the scheduler. Labels carry closed operation names, methods, and statuses only — never URL, host, query, SQL, parameters, keys, or payload content; a log-pipeline failure degrades only logs.
- Local OpenObserve provisioning (pinned `v1.1.2` container, 1-day retention for `_rumdata`/`default`/`kobato_logs`/metric streams, four dashboards, fail-closed RUM allowlist pipeline) and the real `trace:smoke` (traces, metrics, RUM, log↔span correlation) live in `scripts/trace/`; the shared dashboard/VRL assets live under `domains/observability/assets` and are read (never copied) by both the scripts and the server provisioner. They are never imported by the server or by `pnpm test`.
- `email/` copy lives in the SERVER catalog (`messages/server/*`) and every template takes an explicit `t: ServerTranslator` prop; `emailTranslator()` (`infra/email/translator.ts`) resolves the SITE locale at send time, and `<Html lang>` uses that AppLocale. Date-bearing copy stays in the site time zone. USER-AUTHORED content — comment bodies, post titles, site names, music metadata, and the title/body of `direct`/`broadcast` notifications — is passed raw and never translated; SYSTEM notifications render their i18n descriptor through `domains/notifications/message.ts`. `scripts/generate-emails.ts` renders every template in all four locales from a throwaway config.
- `safe-fetch.ts` — THE outbound-fetch surface for user-influenced URLs (SSRF guard: http(s) only, 80/443 port allowlist with a fixed-endpoint opt-out, per-hop DNS-rebinding-validating dial, host revalidation per redirect, credential headers stripped on cross-origin redirects, byte caps). A `trustedOrigin` option is the ONE private-network exemption: only a request whose exact origin matches the fixed, admin-validated endpoint skips the port/private-address guards — connect-time DNS validation included — while every redirect to another origin stays fully guarded. It is wrapped in one CLIENT span (`http.client`) whose only labels are the caller's closed `operation`, method, and upstream status — never URL/host/query. Raw `fetch(` sites in `src/server/` are pinned to an audited allowlist by the boundaries contract test; log lines must use `redactUrlForLog` (`shared/utils/safe-url`) so signed query strings never reach a log.

## domains/

One folder per business domain. Base vocabulary: `schema.ts / repo.ts / service.ts / projection.ts / cache.ts` plus feature-named files. Split by concept cohesion, not line count. Once a subdirectory exists (`services/`, `repos/`), the root file MUST NOT coexist.

- Domains may import `shared/`, `infra/`, other `domains/` — acyclically. When composition would close a cycle, the consumer declares an injected parameter and the caller wires it. A domain's `repos/**` (or root `repo.ts`) is **private** — cross-domain consumers import the surface only.
- `observability/` — Platform leaf for the OpenObserve lifecycle. `config.ts` owns the two fingerprints (CONNECTION → `verifiedFingerprint`; RUNTIME → restart detection) and the Basic-header mapping; `runtime-manager.ts` hot-applies the settings section (fingerprint change → stop/restart, disabled/unverified/invalid → stop, every failure isolated) and surfaces `lastExportError` from `infra/trace/export-health` (per-signal latest OTLP export failure, self-clearing on success) so the panel can warn "running but dropping"; `connection.ts` gates and runs the saved-settings connection test (healthz → authenticated org listing → identifier-preserving org creation → version from `GET /api/<org>/config`); `o2-client.ts` is the bounded, `safeFetch`-based management client for orgs/RUM tokens/functions/pipelines/dashboards (errors are a closed kind + operation + status, never a URL or credential; idempotent GETs retry once after a 250 ms backoff on transient network/timeout failures, mutations never retry); `assets.ts` reads the four bundled v8 dashboards and the fail-closed RUM VRL (SEA blob channel under SEA, disk otherwise) and derives the HMAC `provisionedFingerprint`; `provision.ts` installs the token/pipeline/dashboards idempotently and owns the boot auto-upgrade (`server.ts`, best effort, serialized with the settings writes); `retention.ts` reconciles the OPT-IN stream retention (`retentionDays`, 0 = the operator's OpenObserve policy stays untouched) on every section save, at boot, and once delayed (60 s) after the runtime enters `running` — first-ingest-created streams only exist then — drift-only writes over the Kobato-owned streams (the 1-day dev-container policy stays `scripts/trace`-owned). The `admin.observability.*` procedures live in `http/controllers/admin/observability.controller.ts`.
- Three strata: **Core** (`content`, `posts`, `pages`, `pt`, `settings`), **Feature** (`auth`, `users`, `comments`, `taxonomies`, `images`, `assets`, `fonts`, `music`, `friends`, `newsletter`, `webmentions`, `notifications`), **Platform** (`analytics`, `audit`, `backup`, `update`, `storage`). Platform services are leaves — cross-domain imports INTO them compose at the perimeter. Dedicated docs: `storage` (S3 lock, migration, asset URLs → `domains/storage/AGENTS.md`), `backup` (archive, encryption, restore → `domains/backup/AGENTS.md`). `update/` (SEA self-update) MUST close the listen socket before spawning the replacement (`job.ts::scheduleSelfRestart`) — see `scripts/sea/AGENTS.md`.
- `notifications/` — the message center: `notification` rows fan out at creation into `notification_recipient` (unread = `readAt IS NULL`; later-registered users never see historical broadcasts). Kinds: `direct` (admin ↔ user, always replyable), `admin` (system → all admins, never replyable), `broadcast` (system → all users; admin → all users INCLUDING a pre-read creator self-row; only the admin-created flavor can be replyable, and only NON-ADMIN recipients may answer).
- A reply to a replyable broadcast FORKS a new `direct` thread delivered to all current admins (the replier's own recipient row is pre-marked read); the broadcast root thread only ever contains the announcement itself. Thread reads/replies are gated by `isThreadParticipant` (LIMIT-1 probes — never materialize a broadcast-sized audience); `listThreadParticipantIds` only serves direct-thread reply routing. System producers call `notifyAdmins` — Platform domains get it injected at the composition root (`bootstrap/db-lifecycle.ts`); raw queries live in `infra/db/operations/notification.ts`.
- Recall is a soft delete: `recallNotification` stamps `notification.recalled_at` only where NULL (idempotent), `recallMessage` refuses `direct` messages, and `admin.notifications.recall` audits `notification_broadcast_recalled` / `notification_admin_recalled` ONLY on the first call. Every read path filters `recalled_at IS NULL` — the inbox list and the unread badge drop the message, `getThread` answers NOT_FOUND in the same shape as a missing thread, and `canReplyInThread` refuses new replies on a recalled root. Existing forked direct threads stay readable and replyable.
- Email delivery is a fire-and-forget side effect attached AFTER `createAndFanOut` in the `direct` and `admin` producers only (`notifyAdmins`, `sendDirectMessage`, both `replyToThread` branches) through `email.ts::queueNotificationEmail`: it resolves recipient emails (`findUserEmailsByIds`), renders the shared `AdminNotificationEmail` family and sends one message per recipient sequentially. Gate: `mail.enabled` AND `mail.notificationEmails` (default ON); broadcasts never email, producers keep their synchronous signatures, and a transport failure only reaches the server log. The daily maintenance job prunes READ recipient rows and orphan roots once the message is 180 days old — unread rows are never pruned, and recall itself deletes nothing. System-notification i18n: an `admin`-kind row stores the creation-time ENGLISH fallback in `title`/`body` plus a nullable descriptor (`title_key`/`title_params`, `body_key`/`body_params`); `notifyAdmins` takes typed `notification.*` keys (persisted keys are append-only — never rename/delete, keep params backward-compatible) and validates them at write time. Every read path — inbox preview (truncated from the SAME resolved body at 200 chars), thread detail and notification email — resolves through `domains/notifications/message.ts` with the reader/send locale and falls back to the stored English text (once-logged warning) when the key is gone or its params are malformed. `direct`/`broadcast` rows keep the user's original text and NULL descriptor columns; old rows are never backfilled.

## http/

HTTP perimeter only: `orpc-base.ts` (procedure base), `request-context.ts` (canonical request context), `api-router.ts`, `errors.ts`, `app.ts` (Hono entry), `orpc-trace.ts`; `middlewares/`; `controllers/` (per-domain, admin under `controllers/admin/`); `resources/` (non-JSON: feed, sitemap, images); `loaders/` (React Router data orchestrators); `ssr-caller.ts` (in-process oRPC caller for route loaders). Controllers and loaders **orchestrate only** — business logic stays in `domains/<x>/service.ts`.

- `orpc-trace.ts` is the oRPC transport seam: `app.ts` passes its interceptor as `RPCHandler`'s `clientInterceptors` (HTTP `/rpc/*`) and `ssr-caller.ts` passes it to `createRouterClient({ interceptors })` (in-process). Spans carry the stable router-procedure path plus `orpc.transport=http|in_process`; procedure input is never recorded.
- `buildCspHeader` (`middleware-pipeline.ts`) is the single dynamic-CSP owner and NEVER widens `connect-src`. The browser SDK posts every intake batch to the same-origin relay `POST /api/rum/intake/rum/v1/<org>/rum` (`http/resources/rum-intake.ts`), so the OpenObserve origin appears in no policy and no document and needs no `ZO_CORS_ALLOWED_ORIGINS` entry — an internal (private-IP, plain-HTTP) endpoint is fully supported.
- The relay is mounted in EVERY build next to `/api/rum/status`, exempt from the install gate, excluded from HTTP traces by prefix and from RUM activity by the client URL policy. It reads the SAME verification-gate entry as the browser bootstrap (`frontend-gate.ts` also carries the server-only `FrontendRumRelay` — endpoint/organization/provisioned token/`clientIdentity`), fail-closed-validates the sub-path SHAPE (`/rum/v1/<org-grammar segment>/rum`; the inbound segment is discarded and the upstream always uses the gate's organization), caps query (4 KiB) and body (1 MiB), rate-limits per IP (`tryRumIntakeRateLimit`, 240/min), deletes every inbound `o2-api-key` and appends the real RUM client token, then forwards via `safeFetch` (`trustedOrigin`, 5 s, no redirects, closed `observability.rum.relay` operation) — 202 on success, a detail-free 502 otherwise, never a URL/token in a log. Only with `clientIdentity: 'forward'` does it attach `X-Forwarded-For` (the trusted-proxy-resolved `requestContext.clientAddress`) and the original `User-Agent`; the VRL pipeline still strips the raw address/UA upstream. `/api/rum/status` (`http/resources/rum-status.ts`) is mounted in EVERY build and exempt from the install gate, so it answers `{enabled:false}` even before setup; the gate is read in the handler because a settings change never re-mounts the router. `no-store`, boolean only, excluded from HTTP traces and RUM activity, and supports runtime drift both ways. Rotating the RUM client token and the server authorization header are independent operations; neither ever reaches a document.

### Public content API (`content.*`) and admin domain API

- The public site's read-only data contract is the `content.*` procedure group — a Ghost-Content-API-style surface implemented by `controllers/content-*.controller.ts` (`bootstrap`, `home`, `posts.list/bySlug`, `pages.bySlug`, `comments.byKey`, `search`, `categories.list`, `archives`), with input/output schemas in `shared/contracts/content.ts`. The admin SSR surface lives in the existing domain groups (`account.*`, `comments.*`, `analytics.*`, `admin.*`) with schemas in `shared/contracts/admin.ts`; there is deliberately NO page-level aggregate group — loaders compose domain endpoints themselves.
- Public route loaders and the root loader consume `content.*` through `createSsrCaller` (`ssr-caller.ts`), which runs the router **in-process** against a `HandlerContext` projected from the canonical `RequestContext` — no HTTP hop. It additionally returns `viewer`/`session` for the route-level `requireRole` gates and `isCurrent` projections, since `request-context` is not whitelisted for routes. `ssr-caller.ts` also owns `unwrapListing`/`unwrapDetail`, which translate the output unions back into thrown Responses.
- `loaders/*` helpers are the orchestration layer the content controllers call: `listing`/`search`/`sidebar`/`sidebar-select`/`comments`/`detail` plus the per-endpoint pipelines `page-preview` (pages), `post-detail` (posts — draft fallback, canonical 301) and `home` (the full home listing pipeline — analytics write, settings gates, feature fan-out; `loadHomeData`). Pipelines signal 301/302/404 by throwing `Response`s; `http/content-signals.ts::translateThrownResponse` maps those onto a discriminated signal union (or `ORPCError('NOT_FOUND')`).
- Detail revalidation is not a pipeline: `content-detail.controller.ts` assembles the whole payload (shell, bodyHtml, tags, sidebar, critical), fingerprints it with `postEtag`/`pageEtag` (representation from `context.localization` + published revision + payload) and answers `not-modified` only then; draft previews carry `etag: null` and are never 304'd. Listing procedures (`content.home`, `posts.list`, `search`, `archives`, `categories.list`) revalidate the same way: `runListing`/`runListingPayload` fingerprint the fully assembled payload with `listingEtag` (locale/zone/format + `localization.revisions.listing` + `APP_VERSION` + the site calendar day derived from the payload's OWN `listingNowIso`, so a site-zone midnight cannot split relative-date labels from the tag), answer `not-modified` on a hit, and record the page view ONLY for a served document. `listingLoader` and `searchLoader` take the request-pinned `settings` capture for their page sizes — never a second global-snapshot read.
- Both "random" sidebar widgets are DETERMINISTIC per representation: `selectSidebarPosts`/`selectSidebarTags` sample with a seeded shuffle over entity/URL scope + the site calendar day (in `context.localization.timeZone`) + the settings revision, built once per request by `sidebar-select::sidebarSelection`, with widget counts from the pinned `settings` bundle. Never reintroduce a per-request CSPRNG draw — it would make the detail/listing ETag unmatchable.
- `content.bootstrap` takes no input: it parses the theme cookie itself via `@/shared/utils/theme-cookie` off `context.requestFacts.cookie`, derives the message scope from `context.requestFacts.path` (`/admin` + `/editor` → the complete UI catalog; every other pathname → the `PUBLIC_MESSAGE_PREFIXES` allowlist), ships the active locale's Inkling label table ONLY for a signed-in workspace document (auth/setup pages get the full catalog but no editor labels), ships the request's settings `revision` token as `i18n.revision`, and drops the admin-only `observability` section from the document projection — the OpenObserve endpoint/organization/username and the two verification fingerprints never reach an anonymous document (the settings page reads its own `admin.settings.bootstrap` payload).

### Base procedures

| Base         | Guard                                 | Use for                    |
| ------------ | ------------------------------------- | -------------------------- |
| `publicProc` | No auth gate; `csrfGuard`             | Anonymous + CSRF mutations |
| `authedProc` | `requireAuth` + `csrfGuard`           | Any logged-in user         |
| `authorProc` | `requireRole('author')` + `csrfGuard` | Authors and admins         |
| `adminProc`  | `requireRole('admin')` + `csrfGuard`  | Admins only                |

`csrfGuard` runs on EVERY `/rpc/*` request — safe methods included (`app.ts` mounts it on the whole prefix, and the middleware has no method carve-out). The browser client attaches the `x-csrf-token` header to every call; anonymous sessions validate against the stateless `__csrf` double-submit token minted on safe methods.

### Adding an endpoint

- Schema in `shared/contracts/<domain>.ts` or inline `z.object({...})`; append the procedure to the matching controller with the right base; if the controller isn't in `api-router.ts` yet, add it under `apiRouter` / `apiRouter.admin`.
- A multi-column field-update procedure (PATCH-style: an edit form patches a subset of one row's columns) MUST build its input with `mergePatchInput` from `@/shared/contracts/merge-patch`: the identity key is always a required `id` (never updatable, never declared inside the patch shape), nullable columns use `clearable(...)` (absent = untouched, `null` = clear), and the handler unpacks via `splitMergePatch(input)` instead of hand-rolling `...(x !== undefined && { x })` spreads. Reference implementation: `admin.users.update` in `controllers/admin/users-crud.controller.ts`. The other mutation families are deliberately NOT merge-patch: full-record upserts (`*/upsert`, `*/upsert-meta`, `admin.music.update` — the form owns the whole record), single-field setters (`admin.images.update-note`, `admin.users.mute`, `update-role`), lifecycle actions (`approve`/`delete`/`restore`/…), session-identity profile edits (`account.update-profile` — no caller-supplied id), and the settings section merge.

### Hono / oRPC rules

- No business logic inside procedure handlers.
- Throw `ORPCError('CODE', { message })`; `onErrorHandler` handles the rest. Services never throw `HTTPException`.
- **Error copy is a typed descriptor, not prose.** A migrated producer throws `DomainError`/`ActionFailure` with an `ErrorMessageDescriptor` (`{ messageKey, params?, fallbackMessage }` from `@/shared/contracts/api-error`) as its `message`; the domain keeps the English `fallbackMessage` for logs, and the Hono/oRPC boundaries translate both the top-level message and the issues per request (`context.localization.locale` + `server/infra/i18n`). Every issue on the wire carries the resolved `message` in the request locale ALONGSIDE `messageKey`/`params`/`fallbackMessage`/`code`/`path`; a key never substitutes for text (an unknown key falls back to `fallbackMessage`). `ORPCError.message` is the localized sentence WITH the localized issue summary folded in, and `ORPCError.data` is `{ descriptor, issues }` (never a bare issue array); Hono mirrors `{ error: { code, message, descriptor, issues } }`. Un-migrated domains still pass a raw string — it rides the `error.api.rawMessage` passthrough key and renders unchanged.
- Client-side validation schemas put a typed `UiMessageId` in `message` (never raw copy) and the server maps Zod issues with `server/infra/http/error-descriptor` (`zodIssuesToWire`: id → descriptor + the shared `zodIssueParams` (numeric bounds merged with a custom issue's primitive `params`) + English fallback, the request-locale `message`, producer code, path; standard Zod prose stays an English passthrough). An entity noun crosses as a MACHINE kind (`post`/`page`/`category`/`tag`/`taxonomy`) and the catalog's ICU `select` renders it — never a pre-translated label param, no locale choice in the domain.
- Perimeter middlewares (RBAC, rate limit, timeout, CSRF, body limit) have no `DomainError` channel: they throw `LocalizedHttpException` (`localized-http-exception.ts`) and the same handler translates it; responder-style hooks use `errorJsonResponse`. Controllers that throw `ORPCError` directly use `localizedOrpcError(context, code, messageKey, params?)` from `orpc-base`; a domain helper that already returned a descriptor hands it to `localizedOrpcErrorDescriptor(context, code, descriptor)`. Resource routes that choose their own status from a caught error use `failureJsonResponse(c, error, status?)` / `errorJsonResponse(c, status, key, params?)`.
- A `worker_threads` isolate cannot import `infra/http/errors`: it throws `WorkerDomainError` (`infra/image/process-worker.ts`) carrying the same plain-JSON descriptor, which rides `DomainErrorWire` through the structured clone and rehydrates on the main thread via `domainErrorFromWire` — the descriptor, not the fallback text, is what gets localized.
- Ordinary `Error` is reserved for CLI-only/technical output; a user-visible background failure carries a descriptor instead, and its status boundary localizes it (the self-update job keeps the pipeline's descriptor and `update.status` formats it per request for the VersionDialog). Save-result side-effect warnings are descriptors too — the revision router localizes them into the wire `warning` string (`formatWarningDescriptors`). Auth flows return `AuthFlowResult` with a descriptor (`authFlowError`/`authFlowSuccess`); `routes/auth` resolves it through `authFlowMessage` (the route import whitelist). Settings strict patches reject unknown keys with `unrecognizedKeys` (one issue per key, full key list in `params.keys`, field path preserved).
- No ad-hoc Hono RPC routes bypassing `apiRouter`; non-JSON routes belong in `resources/`. Procedure inputs are a single flat object — no `{ body, query, params }` buckets.

## render/

SSR output products: `seo/`, `feed/`, `og/`, `calendar/`, `canvas-fonts.ts`, `pretext-layout.ts` (canvas text line-breaking via `@chenglou/pretext` — kinsoku-aware wrapping + measured ellipsis for `og/` and `calendar/`; its `OffscreenCanvas` global is shimmed onto @napi-rs/canvas), `analytics/`, `warmup/`. Never persists — produces strings, Buffers, or Responses. Caching is the caller's responsibility, subject to these invariants:

- `feed` and `calendar` cache keys include the request locale + `APP_VERSION` + their SCOPE revision from `shared/config/representation-scopes` (`locale:version:revision:content`), and their HTTP resources (feed, calendar, manifest) answer `Cache-Control: public, no-cache` with a byte-derived ETag + `Content-Language`. The feed generator renders each entry's saved `bodyHtmlFeed` projection (`domains/content/services/body-html.ts::resolveBodyHtmlFeed`, NULL → on-the-fly headless projection) through the `sanitizeFeedHtml` allowlist.
- The feed/calendar/OG resources pass the request context's PINNED `settings` bundle into the renderer (never a second snapshot read), so rendered bytes belong to the scope revision in the key — including the OG card's identity/SEO inputs and either renderer's canvas font family (`canvas-fonts.ts::ensureCanvasFont(slot, settings)` refuses to join a flight for a different family). The sitemap resource keys on the `sitemap` scope (site origin) and renders from the pinned bundle, answering `public, no-cache` with a byte-derived ETag; the manifest and `robots.txt` read the same request capture, not the global snapshot.
- The sidebar's latest-comments digest (`domains/comments/services/public-query::latestComments(db, settings)`) reads SQLite directly — the digest queries are indexed point reads, so no cache bucket or revision key exists for them; the taxonomy sidebar lists (`listAllCategories`/`listAllTags`) read SQLite the same way. Section handlers (`general`/`content`/`assets`/`sidebar`/`fonts`) delete the `feed`/`calendar`/`og`/`sitemap` buckets purely to reclaim orphaned entries — a delete failure reaches the save-warning channel, but correctness comes from the revision key, not the delete.

### Route module prewarming

A Vite plugin splits ~500 client chunks into tiers so the browser proactively loads high-priority routes. At request time, `render/warmup/manifest.ts` matches the pathname against the route tree and emits critical `<link rel="modulepreload">` for the matched route and its ancestor layouts; idle tiers preload lower-priority chunks via inline `<script>`. Tier-2 buckets derive automatically from route-ID prefixes (`routes/public|admin|editor|auth/*`) in `infra/route-warmup.ts` — adding or removing routes in `src/routes.ts` needs no warmup edits. Only `TIER1_ROUTES` is editorial. `tests/unit/server/infra/route-warmup.test.ts` pins every declared route to exactly one bucket.

## Sessions & Request Context

One perimeter middleware derives the canonical `RequestContext` once per request — session, viewer, client address, normalized URL, request facts, db, CSP nonce, plus the PINNED `settings` bundle and the `localization` projection (UI locale + site time zone + `timeFormat` + the boot-token `revision` + the per-scope content-addressed `revisions`).

- Both getters share ONE lazy capture (`createLazyAppSnapshot`), so a settings save mid-request can never split the rendered bytes from their cache key.
- Both `buildLoadContext` for RR loaders AND the `/rpc/*` mount hydrate settings before the capture is first read — the API mount hydrates ahead of the dynamic body-limit resolver and the CSRF guard, which both read settings.
- Every surface (oRPC bridge, RR `buildLoadContext`, resource routers) projects from it — `HandlerContext` carries the same `settings`/`localization` fields. Same-session mutations call `markSessionDirty()`; the middleware commits `Set-Cookie` after the response.

## Databases

Two embedded engines, zero services:

- **Content DB** — SQLite via `node:sqlite` + drizzle (`sqlite-core`), one file at `storage.database` (default `<storage.data>/kobato.db`). Sync driver: awaited builders typecheck OUTSIDE transactions, but `db.transaction(async …)` is a compile error — transactions are sync callbacks. Timestamps are `integer({ mode: 'timestamp_ms' })` (epoch ms), booleans `integer({ mode: 'boolean' })`, JSON `text({ mode: 'json' })`, binary `blob({ mode: 'buffer' })`; `LIKE`, not `ILIKE`.
- **Analytics sidecar** — DuckDB via `@duckdb/node-api`, one file at `storage.analyticsDatabase` (default `<storage.data>/analytics.duckdb`). Holds `access_events` plus the two device-environment sidecars (`device_env_server` — UA-CH high-entropy values + full Accept-Language list, one row per event, written by the enrich pipeline in the same batcher flush as the main row; `device_env_client` — the client beacon's screen/viewport/DPR/touch/color-scheme/network/locale/hardware dimensions, one row per beacon; both keyed by the request-minted event UUID and joined at query time; DDL + appenders in `services/device-env`, the complete table list in `services/schema.ts::ANALYTICS_DDL`).
- `access_events` is a generic-column event table in the Cloudflare-Analytics-Engine style: `index1` entity key (`post:<id>`/`page:<id>`/`''`), 16 opaque `blobN` columns whose semantics live in the `blobsMap` in `domains/analytics/services/access-log` (pinned by a contract test; `blob5` is the daily-salted visitor hash — raw IPs are never persisted; the 16-slot budget deliberately drops `osVersion`/`browserVersion` in favor of `browserType`, and `blob16` is the reserved slot, always written `''`), `double1/2` lat/lng, plus one named `is_bot` boolean.
- Queries are built with Kysely as a compile-only SQL builder (`services/analytics-sql.ts`: DummyDriver, identifier whitelist, bound parameters only) and executed on a dedicated MVCC reader connection through `runAnalyticsQuery`, the single `db.duckdb.query` telemetry boundary (stable operation name only — never SQL or parameters); the batcher writes through the Appender protocol.
- Dashboard metrics own one definition per dimension in `services/metric-dimensions.ts`: a blob slot (`source: 'events'`) or a server-owned bucket expression over `device_env_client` (`source: 'env'`). Env dimensions INNER JOIN the sidecar and drop NULL buckets; blob dimensions never join (beacon-less events must stay visible). An env FILTER is a semi-join built from the same bucket expression, so every dashboard query (views/heatmap/counters/export) honors a clicked env label without joining `device_env_client` itself. Every dashboard query excludes geo-unknown events (country `blob7 = ''`) by default in `services/query-filter.ts` — the wire query's `includeUnknown: true` opts back in (the admin stats 包含未知地区 toggle); writes always keep them.
- The sidecar is recreated empty when missing, but INCLUDED in backups (the `.tar.gz` archive alongside the content DB and the env-converged `kobato.config.json`). DuckDB storage-format upgrade happens at open (`infra/analytics/duckdb.ts`, `COPY FROM DATABASE` through a scratch instance + atomic rename; failure keeps the old file and retries next boot; a `kobato rollback` across the engine bump cannot read the sidecar). A legacy `access_log` table restored from an old backup is migrated by the boot-time one-shot `services/blob-migration.ts` (flag `system.analytics-blob-migration`, probed BEFORE the flag) and then dropped.
- **Backup & restore** (`domains/backup/`) — gzipped tar of the content DB, the analytics sidecar, and the env-converged `kobato.config.json`, optionally password-encrypted (`.enc`). The full contract — record format, restore ordering, crash recovery, upload flow, storage-path validation, audit events — lives in `domains/backup/AGENTS.md`. The 30s global request timeout exempts the restore endpoints (30 min).
- **Page-view counters** — `metric.pv` is written through the in-memory `PageViewBatcher` (`domains/analytics/services/pv-batcher`: flush on 50 bumps of one key or 60s). Reads merge the unflushed delta via `pendingViewDelta`, so served counts stay exact despite the batched write; `domains/comments/services/likes::queryMetadata` is the single read funnel. **Page-view tracking** — `trackPageView` (`domains/analytics/track.ts`) is synchronous: it runs every gate (admin / prefetch / bot), bumps the counter, and returns the request's minted `analyticsEventId` (`RequestFacts`, one per request incl. `.data` — the beacon join key) or `null` when a gate dropped the visit; only the enrich → append tail is async (`flushTrackedEvents()` is the test seam). Every public document tracks exactly one view: home (`loadHomeData`), tag/category listings (`scopedPostsListing`), search (`searchLoader`, after its redirect guards), archives + categories (their `content.*` procedures), and post/page detail (`trackDetailPageView`, called only after the payload ETag revalidation settles — a 304 never records a view); the not-found splat never tracks. Public route loaders publish the same id as loader-data `eid` (`createSsrCaller` → `analyticsEventId`). `AccessLogBatcher` buffers a paired `{ event, envServer }` item and appends `access_events` then `device_env_server` in one flush; legacy flat dead-letter lines replay with a freshly minted id and no sidecar row.
- **Env beacon intake** — `POST /api/analytics/env` (`http/resources/analytics.ts`) is the anonymous `sendBeacon` sink: 4 KB body cap (declared `Content-Length` first, then post-read), the dedicated per-IP bucket `tryDeviceEnvBeaconRateLimit` (120/min, no settings surface), `deviceEnvBeaconSchema` validation, then `pushDeviceEnvBeacon` → the self-registered `DeviceEnvBeaconBatcher` (`domains/analytics/services/env-beacon`, own dead-letter file `ANALYTICS_ENV_DEAD_LETTER_PATH`, `flushDeviceEnvBeacons` test seam). Event ids are deliberately NOT checked against `access_events`: a bot-gated or direct-POST id appends an orphan row that query JOINs drop and the 180-day retention window clears. The batcher pre-filters ids already in `device_env_client` (and duplicates within one batch) before the append — beacons replay on back/forward navigation, StrictMode's dev double effect, and dead-letter replay, and a PK collision would poison the whole appender batch.
- **Daily maintenance** (04:30 site timezone): SQLite `incremental_vacuum` + `optimize` with page/freelist logging plus `job_run` history pruning (30 days / newest 200 per task, `infra/db/job-run-recorder::pruneJobRuns`); DuckDB 180-day retention DELETE on `access_events` + both device-environment sidecars (one cutoff) + `CHECKPOINT` with row/file-size logging (`bootstrap/analytics-lifecycle.ts`); verification-token purge of rows expired >1 day (`domains/auth/token-purge-scheduler.ts`). Pure `ANALYZE` additionally runs after every bulk load (install seed, backup restore). Both DuckDB mutation windows — this retention job and the backup's CHECKPOINT + file copy (`snapshotAnalyticsTo`) — serialize on one module-level mutation lock, so a backup can never copy a file the retention job is mid-DELETE on.
- **`job_run` history** — opt-in execution history for background jobs (trigger, started/finished, duration, status, error), written by `infra/db/job-run-recorder` (wired in `db-lifecycle::wireDatabase`; unwired = silent no-op, writes never throw). Rows left `running` by a crash are swept to `failed` once at boot (`sweepOrphanedJobRuns`, called by `initDatabase` only — the restore rewiring skips it so in-flight jobs of the live process are never mislabeled), writing the stable `process-restart` machine code (shared `JOB_RUN_ERROR_PROCESS_RESTART`) into `error`; the admin task center maps that known code to a locale label while every other stored error renders verbatim.
- **Write batchers** (`infra/db/insert-batcher::FlushLoop` — the insert batchers and `PageViewBatcher` share it): a flush DRAINS. Events buffered while a write was in flight had their triggers swallowed by the singleflight, so a settled flush re-checks the payload and keeps writing until empty. On failure the recovery policy (dead-letter / merge-back) owns the failed batch and the drain stops (no hot-loop), then the loop re-arms the interval timer so rows buffered mid-flush still flush. `pause()/resume()` quiesce every trigger across the backup consistency window; the teardown flush (`flushForTeardown` — shutdown hook, restore swap) ignores the pause gate. `settle()` joins an in-flight flush WITHOUT draining — the never-rejecting quiesce point a teardown awaits before closing the writer underneath (`batcher-registry::settleAllBatchers`; `resetAllBatchers` returns the same join, so a reset that precedes an engine close must be awaited — closing DuckDB connections under an in-flight append is a native use-after-free). `InsertBatcher` caps its buffer (`DEFAULT_MAX_BUFFER_SIZE` = 10_000, five 2048-row DuckDB append chunks) so a stalled writer cannot grow the heap unboundedly: past the cap incoming events are DROPPED (never dead-lettered — a backpressured page view is not worth replaying), counted cumulatively, and surfaced with one warn per drop burst.

## Configuration & Install Gate

- Source of truth: `setting` table — one plain-JSON row per section, `scope='blog.<section>'`. 19 sections defined in `SECTION_REGISTRY` (`domains/settings/sections/registry.ts`). Adding a section = one new module + one registry line.
- In-memory: `BlogSettingsBundle` (`@/shared/config/types`). SSR reads slices via `requireBlogSettingsSection('<key>')`; UI uses per-section hooks. New UI MUST NOT read the whole bundle.
- Install flow: (1) `/admin/setup` creates first admin; (2) sets `blog.general` + `blog.assets`, seeds remaining 17 sections from registry defaults. The shared first-screen locale selector is available before and after Setup Token verification; the install action validates the closed locale set (missing legacy values stay `zh-CN`) and writes the choice into `blog.general.siteIdentity.locale`. `honoInstallGateMiddleware`: no admin → `/admin/setup`; installed → through. "Has admin" == "installed".
- Admin saves: each card POSTs a Section patch; server strict-checks keys, deep-merges, validates against `SECTION_REGISTRY[section].writeSchema ?? .schema` (the write schema is the strict one — hydration and the merge base always use the lenient read schema), writes ONLY that row.

## Content

### Posts and pages

- `post` → `/posts/:slug`; `page` → `/:slug`. Both render the revision's saved `bodyHtml` projection; a NULL column falls back to an on-the-fly headless projection from the Lexical state (`domains/content/services/body-html.ts::resolveBodyHtml`). `visible=false` posts are excluded from home/random-post widgets but stay in archives, tags, search, sitemap, feeds.
- **Draft gate**: a post is public-invisible when `status=draft` OR `publishedRevisionId=null` — all public queries MUST check both. The full "live" gate is defined once in `domains/content/schemas/live-gate.ts` as `isLive` (in-memory) and `liveContentWhere` (SQL). Never hand-assemble the struct.
- **Body projections**: the save pipeline (`domains/content/lifecycle.ts`) computes the revision row's `bodyHtml` / `bodyText` / `bodyHtmlFeed` columns via `infra/pt/lexical-projection.ts` (the `@/inkling/headless` surface, jsdom-backed) over the canonical Lexical state; the feed variant's downgrade (math→TeX, code→plain pre, host-card substitution) is a state-copy transform in `shared/lexical/projection-state.ts`. Projection failure is best-effort (warn + NULL columns), and the no-op save short-circuit skips the computation — the repo/lifecycle share `repos/mutate::isEquivalentToPublishedLatest`. The dashboard「重建文章缓存」button (`admin.renders.reprojectBodies` → `domains/content/services/reproject-body-html.ts::reprojectBodyHtmlBatch`) re-derives the three columns corpus-wide in batches, writing only drifted rows and never `updatedAt` / `clientRevisionToken`.
- **Projection consumers**: feeds render the saved `bodyHtmlFeed`; the search index stores the saved `bodyText` plain text (`indexPostFromRevision` re-derives on the fly only when the column is NULL, and refuses bodies that are not Lexical states); outbound webmention link extraction walks the Lexical state directly (`domains/webmentions/enqueue.ts::extractExternalLinks`), never the HTML; comment notification emails render the comment's saved degraded-HTML `content` snapshot, sanitized at the email boundary (`domains/comments/services/email.ts::sanitizeCommentEmailHtml`).

### Slug derivation

- Canonical: `@/server/infra/slug/derive::deriveSlug(text)` — pipeline `pinyin-pro` → whitespace-collapse → `github-slugger`. Server-only (`pinyin-pro` must not reach the client). The fused explicit-or-derived resolver is `@/server/infra/slug/resolve::resolveSlug`; the route-prefix fence + in-transaction reservation live in `@/server/infra/slug/reservation`. Heading anchors are stored by the save pipeline in the revision's `headings` column (`shared/lexical/collect`); SSR loaders read that projection.
- Page ↔ post slugs share one namespace. Cross-table uniqueness is enforced by the `slug_registry` table: `@/server/infra/slug/reservation::reserveSlugInTransaction` checks it in-transaction, and `@/server/domains/content/slug-conflict::rethrowSlugConflict` maps raced DB `UNIQUE` violations (`{post,page}.slug`, `slug_registry.slug`) to a clean 409.

### Images

- `image` table; bytes in the active storage backend (`infra/storage/registry::activeBackend` — S3 when configured, local filesystem otherwise). Each row persists `storageDriver` so a local→S3 switch keeps old rows readable. Writes use `activeBackend()`, reads/deletes `backendFor(driver)`; whole-fleet scans iterate `allBackends()` — never import a backend directly. S3 configuration, the storage lock, the migration task, key policy, and site-owned asset URLs: `domains/storage/AGENTS.md`.
- Test seam: `__setStorageBackendForTests` / `__resetStorageBackendsForTests` substitute a driver→backend mapping (e.g. `tests/_helpers/memory-storage.ts`) so storage-touching tests run without mocking the registry. All URL → image-meta resolution flows through `domains/images/services/resolve`.

### Audit Log

- **When**: every state-mutating admin operation and auth lifecycle event. Read-only queries MUST NOT. **How**: `recordAuditEventFromContext` from `@/server/domains/audit/services/record`, called after the mutation succeeds. **Naming**: kebab-case present-tense `<entity>_<verb>`; never inline the context extraction.
- **Retention**: DB rows kept `auditLogDbRetentionDays` (default 30), archived daily to S3, then deleted; S3 archives kept `auditLogArchiveRetentionDays` (default 180). **Batcher**: buffered in memory (50 events / 500ms), flushed as one multi-row INSERT in a single sync transaction (`infra/db/insert-batcher`); self-registers with `infra/db/batcher-registry`; flushed on `SIGTERM` / `SIGINT` / `beforeExit`.

### Webmention outbox

- Outbound mentions are DB-persisted rows (`webmention_outbox`, UNIQUE(source,target)) processed by a sequential single-worker loop (`domains/webmentions/outbox`): 5 rows per wake-up, 5 attempts with exponential backoff capped at 12h.
- **Rate semantics**: consecutive batches are at least `OUTBOX_MIN_DELAY_MS` (1s) apart — the scheduler's 'due now' answer is floored (`outbox-scheduler`), so a 50-link burst spaces its sends instead of firing back-to-back. **Waterline**: a scheduled post's rows wait for its publish instant; a republish moving the moment LATER raises a pending row's `nextRetryAt` (one-way — sending late is benign, sending before the source answers 200 burns the retry budget). `sent` rows are never re-sent.

## Server layering constraints

- `infra/*` imports nothing from `domains/`, `http/`, or `render/`.
- `domains/*` imports nothing from `bootstrap/*` — the composition root wires domain deps through `wire*` seams (`wireRestoreMachine`, `wireBackupSnapshots`, `wireAccessLogBatcher`, `wireSessionStorageDb`, …); the boundaries contract test bans the direction outright. Background jobs are the exception that doesn't need wiring: they self-register on `infra/job-registry`.
- `http/controllers/*` and `http/loaders/*` orchestrate only.
- `render/*` produces strings / Buffers / Responses and never persists.
- No barrel `index.ts` files anywhere inside `server/`.
- No `*.server.ts` suffix inside `server/` — it's redundant.
